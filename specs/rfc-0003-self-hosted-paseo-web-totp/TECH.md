# Self-Hosted Paseo Web With TOTP Tech Spec

Product spec: `./PRODUCT.md`

## Current Repo Context

The repo currently has a validated phase-A Passport server and workspace shell
under `specs/rfc-0002-single-user-mvp/`. That implementation proves:

- Fastify server, SQLite persistence, sessions, and protected routes.
- Machine registry and `/api/passport/hosts`.
- Loopback-only local auth bypass.
- Local upstream Paseo CLI/daemon pairing import.
- A generated Passport workspace shell that lists Passport hosts.

The current implementation does not satisfy this spec because:

- Auth is password plus TOTP rather than pure TOTP.
- The workspace is a generated shell, not upstream Paseo `packages/app`.
- Passport-styled pages do not match the upstream Paseo interaction style.
- There is no TOTP enrollment/reset lifecycle.
- There are no access-history or workspace-usage history tables or pages.

## Change Gate

- Problem: Passport must protect and serve the real self-hosted Paseo web app
  with TOTP-only authentication and registry-backed machines.
- Existing path considered: keep the phase-A shell and keep password plus TOTP.
- Why existing path is insufficient: the shell cannot run agents or open
  projects, and password plus TOTP contradicts the desired single-user
  TOTP-only experience.
- Smallest new surface: TOTP enrollment state, TOTP-only login, reset,
  history persistence, Paseo-styled Passport pages, upstream Paseo web
  submodule pinning and patch/build, and replacement of the shell static output.
- What will be deleted or replaced: password auth surface and generated shell
  output are replaced by TOTP-only auth and a patched upstream web build.
- Owner: implementation agents under this spec.
- Validation: TDD for auth state machine, API tests, UI tests where feasible,
  upstream web build validation, local browser smoke against self-hosted Paseo
  UI, and local daemon host availability.
- Temporary or permanent: permanent target for the single-user MVP.
- Removal condition: superseded by a later multi-user or backend-gateway spec.

## Environment Contract

`.env.example` should move toward:

```text
NODE_ENV=development
PASSPORT_HOST=127.0.0.1
PASSPORT_PORT=7317

PASSPORT_SESSION_SECRET=
PASSPORT_DATA_KEY=

PASSPORT_COOKIE_SECURE=false
PASSPORT_DB_PATH=./data/passport.sqlite
PASSPORT_STATIC_DIR=./apps/passport-server/public
PASSPORT_LOCAL_AUTH_BYPASS=false
```

Removed from the target auth contract:

```text
PASSPORT_ADMIN_USER
PASSPORT_PASSWORD_HASH
PASSPORT_TOTP_SECRET
```

TOTP enrollment must be generated by the app and stored in SQLite, not
preconfigured as a static env secret. `PASSPORT_DATA_KEY` is required for
persistent deployments and must protect stored TOTP material with
AES-256-GCM-compatible authenticated encryption. The server must fail closed
when a persistent DB path is used without a valid data key. In-memory tests may
inject a deterministic test key.

`PASSPORT_LOCAL_AUTH_BYPASS=true` remains allowed only for local test runs bound
to `127.0.0.1`, `localhost`, or `::1`.

Verified production-like HK deployment values from 2026-05-04:

```text
PASSPORT_HOST=127.0.0.1
PASSPORT_PORT=6867
PASSPORT_COOKIE_SECURE=true
PASSPORT_DB_PATH=/home/ubuntu/Projects/paseo-passport/data/passport.sqlite
PASSPORT_STATIC_DIR=/home/ubuntu/Projects/paseo-passport/apps/passport-server/public
PASSPORT_LOCAL_AUTH_BYPASS=false
```

That deployment is exposed by Caddy at `https://paseo.codexy.fun:6868`. Caddy
listens on `*:80` for HTTP redirect / certificate issuance and on `*:6868` for
HTTPS reverse proxy to Passport. Existing `*:443` remains reserved for Xray.
Public HTTP origins are not accepted for workspace use because upstream Paseo
relay encryption requires browser WebCrypto and therefore a secure context.

## Data Model

Add or migrate these durable records:

```sql
create table if not exists auth_enrollment (
  id integer primary key check (id = 1),
  totp_secret_encrypted text not null,
  totp_secret_nonce text not null,
  totp_secret_tag text not null,
  enrolled_at text not null,
  updated_at text not null
);

create table if not exists access_events (
  id text primary key,
  event_type text not null,
  outcome text not null,
  occurred_at text not null,
  source_ip text,
  user_agent_hash text,
  details_json text
);

create table if not exists workspace_events (
  id text primary key,
  event_type text not null,
  occurred_at text not null,
  source_ip text,
  server_id text,
  project_key text,
  details_json text
);
```

Existing sessions and machines tables remain, though session user fields should
not imply username/password accounts.

The encrypted TOTP secret fields must use a fresh nonce per enrollment. Reset
deletes the encrypted enrollment row and does not need to decrypt the old
secret.

Allowed access event types:

- `totp_enrollment_started`
- `totp_enrollment_succeeded`
- `totp_login_succeeded`
- `totp_login_failed`
- `logout`
- `totp_reset_succeeded`
- `totp_emergency_reset_succeeded`
- `local_auth_bypass_access`

Allowed MVP workspace event types:

- `workspace_opened`
- `host_profile_loaded`

Deferred workspace event types:

- `host_open_requested`
- `project_open_requested`

Do not implement `host_open_requested` or `project_open_requested` in the MVP.
Keep them reserved for a later upstream UI integration phase.

## API Contract

### Auth State

```http
GET /api/auth/state
```

Returns:

```json
{
  "enrolled": true,
  "authenticated": false
}
```

### Start Enrollment

```http
POST /api/auth/enrollment/start
```

Allowed only when no enrollment exists, unless an authenticated reset flow has
just cleared enrollment. Returns an `otpauth://` URI and QR-code payload for the
browser to render or display.

### Complete Enrollment

```http
POST /api/auth/enrollment/complete
Content-Type: application/json

{"totp":"123456"}
```

On success, persist enrollment, create a session cookie, and record access
history.

### Login

```http
POST /api/auth/login
Content-Type: application/json

{"totp":"123456"}
```

No username or password fields are accepted. On success, create a session
cookie.

Login and enrollment completion failures are rate-limited. The implemented MVP
default is 5 failed attempts per 60 seconds per `request.ip`. The response stays
generic to avoid disclosing whether the request was syntactically valid,
rate-limited, or an incorrect TOTP. Successful authentication clears the bucket;
service restart clears the in-memory buckets.

### Reset Enrollment

```http
POST /api/auth/enrollment/reset
Content-Type: application/json

{"confirm":"reset-totp-enrollment"}
```

Requires auth. Clears enrollment, revokes sessions, records history, and returns
`204`.

### Emergency Reset Command

```sh
npm run passport:reset-totp -- --db ./data/passport.sqlite
```

Runs only on the server machine. It clears TOTP enrollment, revokes all sessions,
records `totp_emergency_reset_succeeded`, and prints a short confirmation. It
must not print the old or next TOTP secret. Passport does not provide a public
web-based recovery flow for lost TOTP devices.

### History

```http
GET /api/admin/history/access
GET /api/admin/history/workspace
```

Both require auth. Responses must be paginated or limited to a safe recent
window. They should include raw source IP for operator audit, but must exclude
secrets, raw User-Agent values, and raw sensitive headers.

Default response page size is 50 rows. Each history category retains the most
recent 3,000 rows. Event writers should prune rows older than the newest 3,000
for their table after successful insert.

### Passport Hosts

`GET /api/passport/hosts` remains protected and returns active machines as
upstream-shaped `HostProfile[]`.

## UI Contract

Passport-owned pages must be restyled to align with Paseo:

- TOTP enrollment surface.
- TOTP login page.
- Machine import and registry page.
- Reset confirmation control.
- Access history list.
- Workspace usage history list.

The UI should use a dark Paseo-like app surface, compact centered auth panels,
clear primary actions, and restrained controls. It should not retain the
phase-A generic light admin-panel look.

The visual contract is anchored to upstream Paseo design guidance in
`vendor/paseo/docs/design-system.md` and tokens in
`vendor/paseo/packages/app/src/styles/theme.ts`. Passport pages are not a
separate security-admin product; they are the local authentication and
operator-entry shell around the self-hosted Paseo web app.

Required visual constraints:

- Overall character is minimal, spacious, quiet, and work-focused.
- Use Paseo-derived neutral app surfaces, foreground, muted foreground,
  border, accent, destructive, radius, spacing, and text scale values. Do not
  introduce a new green/amber security-console palette or saturated gradients.
- Use sentence-case copy and imperative button labels.
- Top-level titles should be light and compact, closer to Paseo screen headers
  than large admin dashboard headings.
- At most one filled primary action appears in a surface. Secondary, row-level,
  reset, and navigation actions should be outline or ghost style unless they are
  inside an explicit confirmation state.
- Destructive color appears only after the operator has indicated destructive
  intent; the reset entry point is quiet and the destructive final action is
  confirmed.
- Settings-like pages use a centered, readable content column and section/card
  groups made of rows with dividers. Avoid nested cards, oversized panels, and
  marketing/admin-dashboard composition.
- Registry and history entries render as dense Paseo-style rows with primary
  and secondary text, optional trailing actions, and no per-row heavy card
  chrome.
- Machine import must show visible success/failure feedback. A successful
  import refreshes the Active hosts registry list in place and announces that
  the hosts were refreshed, so the operator does not need to manually reload the
  page to confirm the imported machine is active.
- Login and first-enrollment flows use compact modal/sheet-like panels inside a
  full-screen app surface. The QR block must be neutral, readable, and stable on
  narrow mobile widths.
- Mobile layouts are first-class: enrollment, login, registry/reset, and
  history must each be screenshot-validated at a 390px-class viewport with no
  horizontal overflow, clipped text, overlapping controls, or unusable QR/manual
  secret content.

When no TOTP enrollment exists, the enrollment UI must be a full-screen
Paseo-styled first-run surface with a centered QR panel. It may visually feel
modal-like, but it is not an overlay on top of the workspace because no
authenticated workspace context exists yet. After successful enrollment, this
QR surface is not shown again unless enrollment is cleared by authenticated
reset or local emergency reset.

Reset must be available from an authenticated settings/admin surface and must
not be a one-click destructive action.

## Self-Hosted Paseo Web Contract

Replace the generated shell with a built upstream Paseo web app:

1. Add upstream Paseo as a git submodule at `vendor/paseo`.
2. Pin the submodule to the latest stable upstream release verified at spec
   time: `v0.1.67`
   (`15a2e3bdcbefda97587f74e499d6b81a278d458c`). Do not pin to prerelease or
   release-candidate tags such as `v0.2.0-rc.1`.
3. Record the upstream repository, release tag, commit, license, and build
   command in `docs/upstream-paseo.md`.
4. Use the confirmed web build command:
   `npm run build --workspace=@getpaseo/app` from `vendor/paseo`, which exports
   to `vendor/paseo/packages/app/dist`.
5. Patch only the minimum host registry boot path needed to load Passport
   hosts: `packages/app/src/runtime/host-runtime.ts`.
   `HostRuntimeStore.runBoot()` must call a new Passport host loader
   immediately after `await this.loadFromStorage();` and before local daemon
   override, E2E, desktop daemon, or localhost fallback handling.
6. Keep Passport-owned patches as tracked files outside the submodule; avoid
   committing modified upstream files directly inside the submodule.
7. Serve the built app from Passport under the protected workspace route.
8. Ensure browser navigation to deep Paseo app routes still falls back to the
   upstream app entrypoint.
9. Preserve upstream local host registry behavior.
10. Ensure same-origin `/api/passport/hosts` requests include Passport cookies.

Agent setup environment:

- Initialize `vendor/paseo` as the git submodule.
- Check out `v0.1.67` in the submodule and verify the submodule HEAD is
  `15a2e3bdcbefda97587f74e499d6b81a278d458c`.
- Do not apply the phase-A placeholder patch to the new release until
  workstream 05 re-confirms the current upstream file paths and regenerates or
  validates the patch against `v0.1.67`.
- Do not commit upstream source modifications inside `vendor/paseo`; keep
  Passport-specific changes as tracked patch files in the parent repo.

The resulting user experience must be the upstream Paseo interactive UI, not a
Passport list shell.

Confirmed host registry patch point:

- `packages/app/src/runtime/host-runtime.ts`
  - `HostRuntimeStore.runBoot()` currently loads browser registry state with
    `await this.loadFromStorage();`.
  - Add `await this.loadPassportHosts();` directly after that call.
  - This runs before configured local daemon override, E2E short-circuit,
    desktop daemon short-circuit, and localhost fallback.
- `packages/app/src/types/host-connection.ts`
  - Reuse `normalizeStoredHostProfile()` to validate Passport host profiles.
- Add `packages/app/src/runtime/passport-hosts.ts`
  - Fetch `/api/passport/hosts` with `credentials: "include"`.
  - Treat `401` as no Passport hosts.
  - Return only normalized `HostProfile[]`.
- Merge by `serverId`, preserving browser-only local hosts.
- Do not persist Passport-loaded hosts into AsyncStorage in the MVP. They are
  server-owned registry data and should be refreshed from Passport each boot.
- Do not change daemon protocol, provider credentials, permissions, project
  open logic, or agent-session logic.

## Security Requirements

- No password storage, password input, or username account model.
- TOTP secret is generated by Passport, stored encrypted with
  `PASSPORT_DATA_KEY`, and never logged.
- TOTP QR code appears only before successful enrollment or after reset.
- Reset requires an authenticated session and explicit confirmation.
- All sessions are revoked after reset.
- Lost-device recovery is local-server-only through the emergency reset command.
- Access and workspace history must store raw source IP for operator audit.
- Access and workspace history must not store TOTP codes, raw cookies, raw
  user agents, raw offers, or provider credentials.
- User-Agent metadata must be stored only as keyed hashes or omitted.
- History `details_json` must use allowlisted fields only.
- Pairing offers remain machine-control credentials.
- Development bypass is loopback-only and records local-test access events.
- Public deployments require HTTPS and secure cookies.
- Behind a reverse proxy, trusted-proxy handling must be configured before raw
  source IP history or IP-based rate limiting can be treated as authoritative.
  This is a known MVP follow-up for the Caddy deployment.

## Validation Plan

Required automated validation:

```text
npm run build
npm test -- --run
```

Additional required checks:

- TOTP enrollment starts only when no enrollment exists.
- Enrollment QR/secret disappears after successful enrollment.
- Enrolled TOTP secret is encrypted at rest; plaintext secret is not stored in
  SQLite, logs, history, or API responses.
- Login accepts only TOTP and rejects username/password payloads.
- Authenticated reset clears enrollment and revokes sessions.
- Emergency reset command clears enrollment and revokes sessions without
  requiring a web session.
- Access history records enrollment, login success/failure, logout, reset, and
  bypass events with source IP and without secrets.
- Workspace history records `workspace_opened` and `host_profile_loaded`.
- Access and workspace history each retain at most 3,000 rows and default to
  50-row pages.
- `/api/passport/hosts` still returns active machines and no raw offers.
- Upstream Paseo web build completes.
- Browser smoke opens the self-hosted Paseo interactive UI through Passport.
- Browser smoke confirms registered Passport hosts are available in that UI.
- Local daemon smoke confirms at least one registered local Paseo daemon can be
  selected or opened in the self-hosted UI.
- Production-like browser smoke confirms the public HTTPS deployment is a
  secure context, the registered `PC-WIN11` host appears in the self-hosted UI,
  and the relay WebSocket is opened from the HTTPS origin.
- Admin UI smoke confirms importing an offer displays success feedback and
  refreshes the Active hosts list without requiring a page reload.

## Risks And Follow-ups

- Upstream Paseo app internals may change. Keep the patch narrow and record the
  exact upstream release tag, commit, and file paths.
- Host-open and project-open usage history may require a broader upstream
  integration than host loading, so they are deferred beyond the MVP.
- TOTP reset is powerful. Later specs may add recovery codes or hardware-key
  recovery, but this MVP remains single-user TOTP only.
- Styling should track upstream Paseo enough for consistency, but avoid copying
  large unrelated UI systems unless needed to serve the real web app.
- Fastify trusted-proxy configuration remains a follow-up before audited raw IP
  history and IP-based rate limiting are fully correct behind Caddy.
- Windows daemon background startup still needs a cleaner service wrapper path
  for hosts where `paseo daemon start` leaves a visible Node console.
